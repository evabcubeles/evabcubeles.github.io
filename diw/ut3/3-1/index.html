3.1 Planificación de una interfaz web

Antes de escribir HTML, aplicar estilos CSS o programar la interacción de una aplicación, es necesario decidir qué se quiere construir, para quién y con qué finalidad. La planificación permite transformar una idea inicial en una propuesta de interfaz organizada y comprensible antes de comenzar su implementación.

En esta fase se analizan los objetivos del proyecto, las personas que utilizarán el producto, sus necesidades y los requisitos que deberá cumplir la interfaz. Estas decisiones servirán de base para organizar posteriormente la información, definir la navegación y construir wireframes y prototipos.

📌 Importante

Diseñar una interfaz no comienza eligiendo colores ni escribiendo código. Comienza comprendiendo el problema que debe resolver y tomando decisiones antes de implementarlas.

El diseño antes de la programación

En desarrollo web es fácil sentir la tentación de empezar directamente a programar. Sin embargo, si todavía no sabemos qué contenidos habrá, qué acciones podrá realizar el usuario o cómo se relacionarán las distintas partes de la aplicación, estaremos tomando decisiones importantes mientras escribimos el código.

Planificar primero permite separar dos problemas diferentes: decidir cómo debe funcionar y organizarse la interfaz y, después, decidir cómo implementarla técnicamente. De este modo es posible detectar errores, comparar alternativas y realizar cambios cuando todavía son rápidos y poco costosos.

❌ Empezar sin planificar

  • Las decisiones se improvisan durante la programación.
  • Es más fácil olvidar contenidos o funciones necesarias.
  • La estructura puede crecer de forma poco coherente.
  • Los cambios importantes obligan a rehacer trabajo ya implementado.

✅ Planificar antes de implementar

  • Se aclaran los objetivos y prioridades del proyecto.
  • Se identifican contenidos, acciones y necesidades.
  • Se pueden estudiar varias soluciones antes de elegir una.
  • El equipo comparte una referencia común para desarrollar la interfaz.
💻 Ejemplo DAW

Si vamos a desarrollar una aplicación para reservar aulas, antes de crear formularios y botones debemos saber quién puede reservar, qué información necesita consultar, qué datos requiere una reserva, qué restricciones existen y qué debe ocurrir después de confirmarla. La interfaz se diseñará a partir de esas decisiones.

Objetivos del sitio o aplicación

Todo proyecto web debe responder a una finalidad. El primer paso de la planificación consiste en formular con claridad qué problema pretende resolver el sitio o la aplicación y qué resultados debe permitir alcanzar.

Un objetivo útil debe ser suficientemente concreto para orientar decisiones posteriores. Expresiones como «hacer una web moderna» o «crear una aplicación atractiva» describen deseos generales, pero no explican qué debe poder conseguir una persona al utilizar el producto.

🎯 Objetivo del producto

Define para qué existe el sitio o aplicación y qué necesidad general pretende cubrir.

👤 Objetivo del usuario

Describe qué quiere conseguir la persona cuando utiliza la interfaz.

⚙️ Funciones necesarias

Concretan qué debe ofrecer el sistema para que esos objetivos puedan cumplirse.

⚠️ Atención

No debemos confundir un objetivo con una solución concreta de diseño. «Permitir al alumnado consultar sus próximas entregas» es un objetivo; decidir que se mostrarán en tarjetas dentro de un panel es una posible solución que podremos valorar después.

Usuarios y necesidades

Una misma aplicación puede ser utilizada por personas con objetivos, conocimientos y responsabilidades diferentes. Por eso, planificar una interfaz exige identificar quiénes serán sus usuarios principales y qué necesitan realizar.

No se trata de diseñar para un «usuario medio» imaginario, sino de reconocer los perfiles relevantes para el proyecto. Podemos considerar, entre otros aspectos, las tareas que realizan, la frecuencia con la que utilizarán el sistema, su experiencia previa, el contexto de uso y las dificultades que podrían encontrar.

Para conocer estas necesidades podemos recurrir a distintas técnicas, como entrevistas, cuestionarios, observación de usuarios, reuniones con las personas implicadas en el proyecto o análisis de un sistema existente. El objetivo es basar las decisiones de diseño en información y no únicamente en suposiciones.

Perfil Necesidad Posible implicación para la interfaz
Estudiante Consultar rápidamente qué tareas tiene pendientes. Dar prioridad a fechas, estados y próximas entregas.
Profesorado Crear actividades y revisar entregas. Ofrecer acciones de gestión claras y acceso a la información del grupo.
Administración Gestionar usuarios, permisos y configuración. Disponer de herramientas específicas de administración sin recargar las vistas del resto.
📌 Idea clave

Conocer al usuario no significa intentar satisfacer cualquier preferencia individual. Significa comprender sus objetivos, tareas y contexto para tomar decisiones de diseño justificadas.

Requisitos de la interfaz

Una vez definidos los objetivos y las necesidades, debemos traducirlos en requisitos. Un requisito expresa una condición o capacidad que el producto debe cumplir y ayuda a convertir ideas generales en decisiones que el equipo pueda comprobar durante el proyecto.

En la planificación de una interfaz podemos encontrar requisitos de distinto tipo. Algunos indican qué acciones debe permitir el sistema; otros establecen condiciones sobre el contexto, los dispositivos, el contenido o determinadas restricciones del proyecto.

Entre estas restricciones pueden encontrarse el tiempo disponible, el presupuesto, las tecnologías que deben utilizarse, los dispositivos de destino, los recursos del equipo o determinadas condiciones establecidas por el cliente o la organización.

Tipo Pregunta que responde Ejemplo
Funcional ¿Qué debe poder hacer el usuario? El estudiante debe poder consultar, filtrar y marcar tareas como completadas.
Contenido ¿Qué información debe mostrarse? Cada tarea debe mostrar título, asignatura, fecha de entrega y estado.
Contexto y dispositivo ¿En qué condiciones se utilizará? Las tareas deben poder consultarse también desde un teléfono móvil.
Restricción del proyecto ¿Qué condición debemos respetar? La interfaz debe seguir la identidad visual definida para el centro.
💻 Ejemplo DAW: de una necesidad a un requisito

Necesidad: «El alumnado quiere saber rápidamente qué entregas tiene próximas». Un requisito podría ser: «La aplicación debe mostrar las actividades pendientes ordenadas por fecha de entrega e indicar claramente su estado». Más adelante decidiremos cómo representar visualmente esa información.

Fases del proceso de diseño

La creación de una interfaz no suele consistir en una única decisión seguida de la programación. Es un proceso iterativo: se analiza el problema, se proponen soluciones, se representan, se revisan y se modifican a medida que obtenemos nueva información.

1. Analizar Comprender objetivos, usuarios, necesidades, contenidos, requisitos y restricciones.
2. Organizar Estructurar la información y definir cómo se relacionarán contenidos, páginas o vistas.
3. Diseñar Plantear soluciones mediante bocetos, wireframes y decisiones visuales.
4. Prototipar Representar y, cuando sea necesario, simular la interacción antes del desarrollo definitivo.
5. Evaluar e iterar Comprobar la propuesta, detectar problemas y mejorarla antes y durante la implementación.

Estas fases no forman una cadena rígida. Por ejemplo, al crear un wireframe podemos descubrir que falta contenido, que una función no está bien definida o que debemos reconsiderar la organización. En ese caso volvemos a una fase anterior, corregimos la propuesta y continuamos.

1Objetivos¿Qué queremos conseguir?
2Usuarios¿Quién lo utilizará y para qué?
3Requisitos¿Qué debe ofrecer y cumplir?
4Diseño¿Cómo organizaremos la solución?
5Revisión¿Funciona la propuesta y qué debemos mejorar?
⚠️ Atención

Planificar no significa intentar decidir cada detalle antes de empezar. Significa reducir la improvisación y disponer de una base razonada que pueda revisarse e iterarse durante el desarrollo.

💭 Piensa

Un cliente solicita una aplicación para gestionar las reservas de las pistas deportivas de un centro. El equipo empieza inmediatamente a diseñar pantallas y programar formularios sin preguntar quién realizará las reservas, qué reglas existen ni qué información debe consultar cada usuario.

¿Qué problemas podrían aparecer? ¿Qué cuestiones debería aclarar el equipo antes de continuar?

Ver una posible solución

El equipo podría diseñar funciones innecesarias, olvidar requisitos importantes o construir una estructura que después resulte difícil de modificar. También podría asumir incorrectamente que todos los usuarios realizan las mismas tareas.

Antes de continuar debería aclarar, entre otras cuestiones, el objetivo del sistema, los perfiles de usuario, las tareas que realizará cada perfil, los datos necesarios, las reglas de las reservas, los dispositivos y contextos de uso y las restricciones del proyecto. Con esa información podrá definir requisitos y comenzar a organizar la interfaz con mayor criterio.
