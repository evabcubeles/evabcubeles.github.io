7.8 Pruebas y verificación del diseño responsive

En el apartado 7.7 aprendimos a construir distribuciones responsive con Bootstrap 5. Sin embargo, que una página utilice media queries, Flexbox, CSS Grid o Bootstrap no garantiza que se vea y funcione correctamente en todas las pantallas.

En este apartado aprenderemos a probar, detectar y corregir errores en una interfaz responsive. Utilizaremos las herramientas de desarrollo del navegador y el proyecto StudyFlow para comprobar la distribución, el contenido y la interacción.

📌 Importante

Un diseño responsive no se verifica únicamente comprobando que se ve bien en un móvil y en un ordenador. También debemos probar anchuras intermedias, orientación, contenido real y elementos interactivos.

Por qué debemos verificar un diseño responsive

Durante el desarrollo podemos encontrar tarjetas que se salen de su contenedor, menús difíciles de utilizar, textos cortados o imágenes deformadas. Estos problemas pueden aparecer solo en determinados tamaños de pantalla.

La verificación responsive consiste en comprobar de forma sistemática que la interfaz se adapta, mantiene la legibilidad y permite completar las tareas previstas en diferentes condiciones.

AspectoQué debemos comprobar
DistribuciónQue las columnas, tarjetas y menús se reorganizan correctamente.
ContenidoQue textos, tablas, imágenes y vídeos siguen siendo utilizables.
InteracciónQue enlaces, botones y formularios se pueden manejar con comodidad.
ContinuidadQue no aparecen fallos al pasar de una anchura a otra.

Herramientas para realizar las pruebas

Los navegadores modernos incluyen herramientas de desarrollo (DevTools) con un modo de simulación de dispositivos. En Chrome o Edge podemos abrirlas con F12 y activar la barra de dispositivos con Ctrl + Mayús + M (o mediante su icono). Los atajos pueden variar según el navegador y el sistema operativo.

  1. Abre la página de StudyFlow en el navegador.
  2. Abre las herramientas de desarrollo y activa el modo de dispositivos.
  3. Selecciona una anchura de viewport o escribe un valor personalizado.
  4. Modifica progresivamente la anchura y observa cómo cambia la distribución.
  5. Repite las pruebas con orientación vertical y horizontal cuando sea relevante.

La simulación es útil para localizar problemas, pero no reproduce por completo un dispositivo físico: pueden existir diferencias de rendimiento, entrada táctil, tipografías y comportamiento del navegador.

Comprobación de anchuras y puntos de ruptura

No es suficiente probar únicamente valores conocidos como 768 px o 992 px. Conviene verificar justo antes, en el propio breakpoint y justo después, además de otras anchuras intermedias. Un diseño puede fallar a 740 px aunque funcione a 375 y 1024 px.

CSS · Ejemplo de puntos de ruptura de StudyFlow
.modulos {
  display: grid;
  grid-template-columns: 1fr;
  gap: 16px;
}

@media (min-width: 768px) {
  .modulos { grid-template-columns: repeat(2, minmax(0, 1fr)); }
}

@media (min-width: 992px) {
  .modulos { grid-template-columns: repeat(3, minmax(0, 1fr)); }
}

Con estas reglas, podemos comprobar, por ejemplo, 767, 768 y 769 px, y después 991, 992 y 993 px. Los puntos de ruptura deben responder a las necesidades del contenido; no debemos confundirlos con modelos concretos de dispositivos.

Detección de desbordamientos y errores de maquetación

Uno de los problemas más habituales es el desbordamiento horizontal: algún elemento ocupa más espacio que el viewport y aparece una barra de desplazamiento horizontal no prevista.

Las causas pueden ser anchuras fijas excesivas, imágenes sin límites, cadenas largas que no se pueden partir, tablas anchas o elementos flexibles que no pueden reducirse.

JavaScript · Comprobar si existe desbordamiento horizontal
const anchoDocumento = document.documentElement.scrollWidth;
const anchoViewport = document.documentElement.clientWidth;

if (anchoDocumento > anchoViewport) {
  console.warn("Posible desbordamiento horizontal:",
               anchoDocumento - anchoViewport, "px");
} else {
  console.log("No se detecta desbordamiento horizontal global.");
}

Este código se puede ejecutar en la consola de DevTools. Compara la anchura total desplazable del documento (scrollWidth) con la anchura visible del elemento raíz (clientWidth).

Si scrollWidth es mayor que clientWidth, existe una diferencia que puede indicar desbordamiento horizontal global. Sin embargo, no identifica automáticamente el elemento responsable ni detecta todos los problemas de distribución, como contenido recortado dentro de un contenedor o elementos superpuestos. Por eso debemos complementar esta comprobación con una inspección visual.

CSS · Correcciones habituales
img, video {
  max-width: 100%;
  height: auto;
}

.contenedor-flexible {
  min-width: 0;
}

.texto-largo {
  overflow-wrap: anywhere;
}

.tabla-contenedor {
  max-width: 100%;
  overflow-x: auto;
}

La propiedad min-width: 0 resulta especialmente útil en elementos que participan en distribuciones con Flexbox o CSS Grid. En determinadas situaciones, estos elementos mantienen un tamaño mínimo basado en su contenido y pueden impedir que la distribución se reduzca correctamente. Al establecer min-width: 0, permitimos que el elemento pueda estrecharse por debajo de ese tamaño mínimo automático. Esto no garantiza por sí solo que todo su contenido se adapte, por lo que también debemos revisar imágenes, textos y posibles desbordamientos internos.

⚠️ Atención

Aplicar overflow-x: hidden al body puede ocultar la barra de desplazamiento, pero no soluciona la causa del desbordamiento y puede dejar contenido inaccesible.

Verificación de imágenes, textos e interacción

Una interfaz puede tener las columnas bien distribuidas y seguir siendo difícil de utilizar. Por eso también debemos comprobar cómo se comporta el contenido real.

  • Imágenes y vídeos: mantienen proporciones, no se salen de su contenedor y no recortan información importante.
  • Textos: son legibles, se ajustan a la anchura disponible y no quedan tapados por otros elementos.
  • Tablas: conservan sus datos y, cuando es necesario, permiten desplazamiento horizontal dentro de un contenedor.
  • Menús y botones: siguen siendo visibles, comprensibles y fáciles de activar.
  • Formularios: las etiquetas y campos se muestran correctamente y se pueden completar.
  • Zoom y teclado: comprobar que, al aumentar el zoom del navegador, el contenido sigue siendo legible y utilizable sin pérdidas importantes de información o funcionalidad. También debemos verificar que podemos recorrer los controles mediante la tecla Tab, que el foco de teclado es visible y que el orden de navegación resulta lógico.

La comprobación responsive se relaciona con la accesibilidad y la usabilidad, aunque no las sustituye: esas materias requieren verificaciones adicionales.

Imagina que hemos terminado el panel de módulos de StudyFlow. Antes de darlo por válido, elaboramos una pequeña lista de comprobación y registramos los problemas encontrados.

Los puntos de ruptura determinan cuándo se aplican determinadas reglas CSS, pero no garantizan que el contenido se visualice correctamente. Por ejemplo, aunque una media query establezca tres columnas desde 992 px, debemos comprobar que los títulos, botones e imágenes caben dentro de cada tarjeta. Si no es así, tendremos que revisar las dimensiones, los espacios disponibles o incluso los puntos de ruptura elegidos.

JavaScript · Informe básico de comprobación
function comprobarDesbordamiento() {
  const documento = document.documentElement;
  const exceso = documento.scrollWidth - documento.clientWidth;

  return {
    viewport: documento.clientWidth,
    desbordamientoHorizontal: exceso > 0,
    excesoEnPixeles: Math.max(0, exceso)
  };
}

console.table(comprobarDesbordamiento());

Este informe sirve como apoyo a la inspección visual, pero debemos revisar manualmente los componentes, la interacción y las diferentes anchuras. Si detectamos un error, conviene registrar anchura, elemento afectado, comportamiento observado y corrección aplicada para poder repetir la prueba.

💻 Ejemplo DAW

Si la tabla de calificaciones de StudyFlow provoca desplazamiento horizontal de toda la página a 390 px, podemos colocarla en un contenedor con overflow-x: auto y verificar que el desplazamiento queda limitado a la propia tabla.

Buenas prácticas y errores frecuentes

  • Probar de forma progresiva: no limitarse a dos o tres tamaños predefinidos.
  • Revisar los límites: comprobar las anchuras cercanas a cada breakpoint.
  • Usar contenido representativo: incluir textos largos, imágenes y datos similares a los reales.
  • Investigar el origen del fallo: no ocultar los desbordamientos sin corregirlos.
  • Combinar herramientas y pruebas reales: la simulación del navegador no sustituye todas las comprobaciones en dispositivos físicos.
  • Verificar la interacción: comprobar menús, botones, enlaces, formularios y navegación por teclado.
  • Repetir las pruebas: una modificación CSS puede corregir una anchura y provocar un fallo en otra.
📌 Idea clave

Un diseño responsive está terminado cuando hemos comprobado su distribución, su contenido y su funcionamiento en distintas anchuras, y hemos corregido los problemas detectados. Las pruebas deben formar parte del desarrollo, no dejarse únicamente para el final.

💭 Piensa

Al probar StudyFlow a 390 px, observas que aparece una barra horizontal en toda la página. Además, una tabla de calificaciones es demasiado ancha y el botón del menú queda parcialmente oculto. ¿Cómo investigarías cada problema? ¿Sería correcto solucionarlo todo añadiendo overflow-x: hidden al body?

Ver una posible solución

Primero comprobaría el desbordamiento global con DevTools y revisaría los elementos que sobresalen. Inspeccionaría la tabla y su contenedor para decidir si necesita desplazamiento horizontal propio; después comprobaría el ancho, las reglas CSS y la posición del botón del menú.

No aplicaría overflow-x: hidden al body como solución general, porque podría ocultar contenido sin resolver el problema. Tras corregir cada elemento, repetiría las pruebas a 390 px y en otras anchuras, especialmente cerca de los puntos de ruptura.
