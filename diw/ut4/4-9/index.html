4.9 Buenas prácticas y validación del HTML

Escribir HTML no consiste únicamente en conseguir que una página se muestre en el navegador. Un documento puede visualizarse aparentemente bien y, sin embargo, contener errores de estructura, elementos mal utilizados o código difícil de mantener.

Por ello, al desarrollar una interfaz debemos procurar que el código sea válido, legible, semántico y coherente. Además, existen herramientas que permiten comprobar automáticamente parte de estos aspectos y detectar errores antes de publicar una página.

📌 Importante

Que el navegador muestre una página no significa que su HTML sea correcto. Los navegadores intentan interpretar incluso documentos con errores, por lo que debemos revisar y validar nuestro código.

Código HTML válido y bien estructurado

Un documento HTML bien estructurado respeta las reglas del lenguaje y utiliza correctamente sus elementos y atributos. Esto implica, entre otros aspectos, mantener una estructura básica adecuada, anidar correctamente los elementos y evitar construcciones no permitidas.

HTML · Estructura correcta
<article>
  <h2>Proyecto de interfaz</h2>
  <p>Diseña una interfaz para la aplicación propuesta.</p>
</article>

El anidamiento debe reflejar correctamente qué elementos están contenidos dentro de otros. Las etiquetas deben cerrarse en el orden adecuado.

HTML · Anidamiento incorrecto
<p>Consulta la <strong>fecha de entrega</p></strong>
HTML · Anidamiento correcto
<p>Consulta la <strong>fecha de entrega</strong>.</p>

También debemos respetar las restricciones propias de cada elemento. Por ejemplo, los valores de id deben ser únicos dentro del documento y determinados elementos solo admiten ciertos contenidos o atributos.

⚠️ Atención

No debemos corregir el HTML únicamente hasta que «se vea bien». Una estructura incorrecta puede provocar comportamientos inesperados y dificultar el mantenimiento del proyecto.

Indentación y legibilidad

La indentación consiste en desplazar visualmente el código para mostrar la relación entre elementos padre e hijos. El navegador no necesita una indentación concreta para interpretar HTML, pero las personas sí se benefician de un código ordenado y consistente.

HTML · Código difícil de leer
<main><section><h2>Entregas</h2><p>Consulta tus actividades.</p></section></main>
HTML · Código indentado
<main>
  <section>
    <h2>Entregas</h2>
    <p>Consulta tus actividades.</p>
  </section>
</main>

Además de indentar, conviene mantener un criterio uniforme: utilizar nombres claros para clases e identificadores, separar bloques cuando facilite la lectura y evitar cambios arbitrarios de formato dentro del mismo proyecto.

💻 Ejemplo DAW

En un proyecto desarrollado por varias personas, una estructura y un formato coherentes permiten localizar errores, revisar cambios y comprender con mayor rapidez el código escrito por otros miembros del equipo.

Separación entre contenido y presentación

HTML debe describir principalmente la estructura y el significado del contenido, mientras que CSS se encarga de su presentación visual. Mantener esta separación hace que el código sea más claro, reutilizable y fácil de mantener.

Por ejemplo, no debemos elegir una etiqueta porque el navegador la muestre con un determinado aspecto. Si queremos modificar colores, tamaños, márgenes, posiciones o distribuciones, utilizaremos CSS.

HTML · Separación de responsabilidades
<!-- Evitar como práctica general -->
<p style="color: green; font-size: 22px;">Entrega completada</p>

<!-- Preferible -->
<p class="estado-completado">Entrega completada</p>

La clase describe el propósito del elemento y permite trasladar las reglas visuales a la hoja de estilos. Estudiaremos con detalle CSS en las siguientes unidades.

⚠️ Atención

El atributo style es válido, pero incluir de forma generalizada estilos en línea mezcla contenido y presentación y dificulta el mantenimiento. En un proyecto organizado, normalmente preferiremos hojas de estilo CSS.

Uso adecuado de elementos semánticos

La semántica también forma parte de la calidad del código. Debemos seleccionar los elementos según la función real del contenido y no únicamente según su apariencia predeterminada.

SituaciónElección adecuada
Título de una secciónUtilizar un encabezado adecuado, como <h2>, en lugar de un párrafo grande mediante estilos.
Navegación principalUtilizar <nav> cuando el bloque constituye una sección importante de navegación.
Botón que ejecuta una acciónUtilizar <button> en lugar de convertir un <div> en un control mediante JavaScript.
Lista de elementosUtilizar <ul> u <ol> cuando el contenido representa realmente una lista.
Datos tabularesUtilizar una tabla cuando existe una relación tabular entre los datos, no una sucesión de contenedores creada únicamente para imitar filas y columnas.
📌 Idea clave

Un HTML de calidad no intenta utilizar etiquetas «más modernas» por sistema. Utiliza el elemento que describe correctamente cada contenido y recurre a elementos genéricos cuando no existe otro más apropiado.

Errores frecuentes

Durante el desarrollo de una página es habitual cometer pequeños errores. Algunos pueden detectarse visualmente, pero otros pasan desapercibidos porque el navegador intenta recuperarse de ellos al interpretar el documento.

ErrorProblemaQué revisar
Etiquetas mal anidadasLa estructura del documento no representa correctamente la relación entre los elementos.Orden de apertura y cierre.
id duplicadosDos elementos comparten un identificador que debe ser único.Asignar un valor de id diferente a cada elemento.
Atributos necesarios ausentesEl elemento puede quedar incompleto o perder información necesaria.Por ejemplo, revisar el atributo alt de las imágenes.
Elementos utilizados por su aparienciaSe pierde significado semántico.Elegir el elemento según la función del contenido.
Enlaces o rutas incorrectasEl recurso no puede localizarse.Comprobar rutas relativas, nombres de archivo y estructura de carpetas.
Contenido y presentación mezcladosEl código resulta más difícil de mantener.Trasladar la presentación a CSS cuando corresponda.

Elementos obsoletos y técnicas antiguas

HTML ha evolucionado y algunas técnicas utilizadas en versiones antiguas dejaron de formar parte del HTML actual. Es importante reconocerlas cuando aparecen en materiales antiguos, pero no debemos utilizarlas como solución para proyectos nuevos.

Un ejemplo son <frameset> y <frame>, que antiguamente permitían dividir la ventana del navegador en diferentes documentos. Estos elementos son obsoletos y no forman parte del HTML actual. La estructura y distribución visual de una página moderna se realiza mediante HTML semántico y CSS.

⚠️ Atención

<iframe> es diferente de los antiguos <frame> y <frameset>. <iframe> sigue formando parte de HTML y permite incrustar otro documento HTML o determinados contenidos externos dentro de una página. No debe confundirse con la antigua maquetación mediante marcos.

Validación del documento HTML

La validación consiste en comprobar si el documento cumple las reglas sintácticas y estructurales aplicables al HTML actual. Un validador analiza el código y señala errores, advertencias o construcciones que conviene revisar.

Una herramienta de referencia es el Nu Html Checker , que permite comprobar documentos HTML y detectar problemas relacionados con el marcado.

💻 Procedimiento de comprobación

Durante el desarrollo podemos validar periódicamente nuestras páginas, revisar los mensajes obtenidos, corregir los errores y volver a ejecutar la comprobación. Este proceso resulta especialmente útil antes de entregar o publicar un proyecto.

📌 Importante

La validación automática es una ayuda, no una garantía de calidad total. Que un documento no presente errores de validación no significa que su interfaz sea necesariamente accesible, usable o adecuada para sus usuarios. Estos aspectos se estudiarán específicamente en las unidades correspondientes.

¿Cómo interpretar los resultados?

Los mensajes de un validador deben leerse con atención. Un error puede provocar otros mensajes posteriores, por lo que conviene empezar por los primeros problemas detectados, corregirlos y volver a validar.

  • Error: indica un problema que debe revisarse y corregirse.
  • Advertencia: señala una situación que merece atención aunque no siempre impida que el documento sea procesado.
  • Información: puede aportar contexto adicional sobre el documento o sobre determinadas prácticas.
💻 Ejemplo DAW

Antes de entregar una interfaz de StudyFlow, el equipo valida sus páginas HTML. Si aparecen errores de anidamiento, identificadores duplicados o atributos incorrectos, los corrige y vuelve a validar. Después realiza por separado las comprobaciones de accesibilidad, usabilidad y funcionamiento previstas para el proyecto.

📌 Idea clave

El objetivo no es conseguir únicamente que el validador «se ponga en verde», sino utilizar la validación como parte de un proceso de desarrollo basado en código correcto, comprensible, semántico y mantenible.

💭 Piensa

Un alumno entrega una página que se visualiza correctamente en su navegador. Sin embargo, ha utilizado varios id repetidos, algunas etiquetas están mal anidadas, gran parte de la presentación está escrita mediante atributos style y no ha validado el documento.

¿Considerarías suficiente comprobar únicamente que la página «se ve bien»? ¿Qué pasos debería realizar antes de dar el HTML por terminado?

Ver una posible solución

No. Primero debería revisar la estructura del documento y corregir el anidamiento y los identificadores duplicados. También convendría separar la presentación del contenido trasladando los estilos a CSS cuando corresponda.

Después debería validar el documento, interpretar los mensajes obtenidos, corregir los problemas detectados y volver a validar. Finalmente, deberá realizar otras comprobaciones específicas —como accesibilidad, usabilidad y funcionamiento— que no quedan garantizadas por una validación HTML correcta.
